## What changed, by finding

**M27 — the final merge held the write lock for its whole duration.** Baseline measured first: on a synthetic 100,000-variant × 4-sample VEP VCF the merge phase took ≈8 s and a concurrent writer waited 6.1 s (the reviewer reproduced blocked library/phenotype writes with a shortened timeout; a whole genome extrapolates to minutes and the 60 s timeout). `cohort_store._merge_stages` was restructured (`MERGE_CHUNK_VARIANTS = 5,000`):

- *Phase 0* (short transaction): the new `cohort_files` row is inserted as `import_state='merging'` under a NUL-marked path that no lookup matches; sample ids are reserved from a new `cohort_meta.next_sample_id` allocator into a TEMP mapping table; `merge_cleanup_pending` is set.
- *Phase 1* (one bounded transaction per key range): variants, annotations, prediction observations/values and genotypes are upserted per range of staged variant keys, with foreign keys off on the merge connection so genotypes can reference the reserved sample ids before their rows exist. Between transactions the merge yields — 10 ms always, and a full busy-handler poll interval (150 ms) when another request in the service has declared write intent (`WriteCoordinator`; `begin/end_storage_mutation` declare it for every mutating request), because SQLite's busy handler cannot take a lock that is released and re-taken within microseconds.
- *Phase 2* (short "publish" transaction): the sample rows are inserted (this is the moment the file becomes visible), the replaced file's samples and row are removed in the same transaction (atomic swap, no window with both or neither), the real path and `import_state='ready'` are set with the counts.
- *Phase 3* (bounded): the replaced file's genotypes/observations are reclaimed in chunked deletes, orphan variants are removed in chunks (cascading their annotations), the withheld-PromoterAI reconciliation re-runs for the touched rows now that the old file's observations are gone, secondary indexes (first file only) are built one per transaction, and the pending flag is cleared.
- *Recovery*: a database opened with a `merging` file or `merge_cleanup_pending` set (crash, kill, power loss at any phase) drops the unpublished file, deletes dangling genotypes/observations/values and orphan variants in bounded transactions, and clears the flag; the import can simply be repeated. `stats()`/`profiles()` count only `ready` files (`stats().merging_files` is new).
- The service answers a lock timeout during an active import with HTTP 409 `import_finishing` ("An import is finishing … retry in a moment") instead of a 500.

After: max concurrent-writer wait 0.85 s on the same 100k×4 import (0.93 s without intent, 1.7 s on a 300k×2 first-file import whose tail is an index build) — bounded per chunk, independent of file size. Tests: `ChunkedMergeTests` (nothing partial visible at any commit; a 0.3 s-timeout writer succeeds on every attempt during a slowed 20-chunk merge; in-merge failure cleans up; a simulated hard crash is recovered on the next open and the file then imports cleanly; forced re-import swaps atomically with exactly one published file at every commit) and the 409 boundary test in `test_http_validation.py`. Documented in `docs/SAMPLE_LIBRARY_AND_STORAGE.md` ("Imports and concurrent editing"). Existing databases gain the `import_state` column on open.

**M28 — projection files survive removal (cleanup half).** New `projections` cleanup category removes every cached per-sample review projection (rebuilt on demand); any other cleanup reaps *orphaned* projections (no dataset references their managed file); `storage_stats().locations.projections` reports their size; the Storage page's cleanup includes the category and says so. Tests: `test_cleanup_reclaims_review_projections`. Documented.

**M29 — SCREEN matrix stride mismatch.** `ScreenContextStore._configure` now derives one stride per matrix from the prepared manifest's shape, verifies each matrix file is exactly rows×columns bytes and that every catalog tissue index / profile index lies within its matrix width (an inconsistent bundle is refused with a clear error instead of misread), and both the detail evidence reader and the filter read through the same geometry. Tests: the reviewer's exact skew (two-column matrix, one-entry catalog: detail and filter now agree on the second cCRE row; failed on the old reader) and the refusal cases.

**M30 — migration recovery.** Sample Library schema changes are an ordered list of named steps (`library_versions_v1`, `library_current_uniqueness_v1`, `portable_paths_v2`), each executed in one explicit transaction together with its marker (`isolation_level=None`; SQLite DDL is transactional), so a crash between ALTER and backfill rolls the step back and the next open repeats it. A recorded step is re-applied when the schema contradicts it (columns/indexes missing, rows with `version_id=''`), so a partially restored database still converges; `library_schema_version` and `migration_status()` expose the state. The reviewer's interruption (columns present, no backfill) is now completed on the next open: `cohort_preferred` follows `include_in_cohort`, version ids come from the legacy grouping rule. Tests: `test_interrupted_column_migration_is_completed_on_the_next_open`, `test_migration_step_is_atomic_with_its_marker` (both fail on the old code). Documented ("Schema migrations").

**M31 — CSQ processing, benchmarked before touching anything.** Profile of the staging parser on a synthetic 50,000-record × 4-sample VEP VCF: annotation normalisation (per-transcript predictor and PromoterAI provenance rules) dominates; `decode`/`parse_csq_entries` together are ≈20%; the review's "dominated by decoding" and "10× faster" were not supported. Equivalence-preserving changes: `decode` skips `unquote` when no `%` is present; `parse_csq_entries` builds each entry with one `zip` (short rows padded, extra values ignored, as before); the PromoterAI observation is evaluated once per annotation row instead of twice; CSQ is decoded only once a selected sample is known to carry an alternate allele (a restricted re-index of one sample in a joint file no longer decodes every record); the whole-genome prefilter derives per-header dataset flags once per header instead of per record. Measured against the pre-change code on the same input: full staging 286 → 232 µs/record (−19%), restricted 129 → 94 µs/record (−27%), prefilter `evaluate_record` 56 → 42 µs/record (−25%). Tests: byte-for-byte decode equivalence against `unquote`, parser padding/overflow cases, and a laziness test counting parser calls for carried vs non-carried records; the header-flag cache test in `test_wgs_review.py`. Documented with the numbers.

## Follow-up — second review round (written 2026-09-08 ≈01:45 UTC)

The reviewer reproduced four remaining gaps, the first a data-integrity problem my chunked merge introduced. All four were reproduced here first, then fixed; six files rewritten on the Mac (`local_service/cohort_store.py`, `local_service/sample_library.py`, their two test files, `docs/SAMPLE_LIBRARY_AND_STORAGE.md`, `docs/REVIEW_WORKBENCH.md`), each verified unchanged since 23:52 before writing and re-hashed afterwards (6/6 identical; `cohort_store.py` kept its executable bit). Nothing staged or committed.

**M27 — a failed re-import must leave the previous cohort untouched (the stated priority).** Two causes, both mine: the chunks upsert into tables shared by every file (variants, transcript annotations; for a sample-restricted re-import also the file's own prediction observations/values), so a failure after *n* chunks left the first *n* chunks' rows carrying the new file's scores; and the append path deleted the addressed samples' old rows in phase 0, so a failed restricted re-import of P1 left only P2.

- *Merge journal.* Every chunk now first records, inside its own transaction, the pre-image of each existing row its upserts (and the PromoterAI reconciliation) may change, and the id of every row it inserts — four journal tables in the database (`merge_journal_variants/annotations/observations/values`, pre-image columns declared without a type so values round-trip exactly; empty outside a merge). Inserted ids are found by rowid floor (rows above the table's MAX(id) before the upsert, exact within the transaction); pre-images are selected from the chunk's stage key range outward (`CROSS JOIN`, and a unary `+` on the file-id term so the planner uses the variant index — the first draft rescanned every observation of the file per chunk). Observation/value journaling happens only for appends, the one case where an existing file id owns rows the upsert can conflict with.
- *Rollback.* `_rollback_merge_journal` restores pre-images in bounded transactions (children first), then deletes inserted rows with cascades on; the reserved-sample genotypes and the unpublished file row go through the existing cleanup. It runs in the failure path and, from the journal that survived in the database, on the next open: `merge_cleanup_pending` is now `merging:<id>` until the publish transaction and `published:<id>` until reclamation finished (a bare id from the 23:52 build is read as published unless a `merging` file row shows otherwise), so recovery rolls back only unpublished merges.
- *Append path.* The addressed samples' old rows are no longer removed before publication; they are retired in the publish transaction, in the same step their replacements appear, and their genotypes/observations are reclaimed afterwards like a replaced file's. Readers see the previous state until then.
- *Indexes.* When the only file is being replaced the secondary indexes are dropped in phase 0; they are now rebuilt *before* the reclamation/rollback rather than after — their absence made every cascade a table scan (the 100k rollback took minutes; 2.9 s with the indexes back) — and the failure path rebuilds them too, so the surviving rows never stay unindexed.
- A process-level lock serialises `_merge_stages`; the journal and the marker describe one merge.

Measured on the 100,000-variant × 4-sample synthetic file, merge phase only: first import 11.6 → 12.7 s, forced replacement 15.8 → 17.2 s, sample-restricted append 9.5 → 12.5 s (the journal writes are inside the chunk transactions, so the per-chunk lock hold grows by the same ~9–30%, still a fraction of a second). Rollback of a replacement failed after 19 of 24 chunks: 2.9 s, every annotation back to its pre-image (one CADD value in the table afterwards, the old one). Tests (`ChunkedMergeTests`): `test_failed_forced_replacement_leaves_the_previous_cohort_untouched` (full-table snapshot equality of variants, annotations, genotypes, observations, samples and files; journal empty; indexes present; the retry then replaces everything), `test_failed_sample_restricted_reimport_keeps_the_addressed_sample` (P1 and P2 both there and identical; retry indexes P1 exactly once), `test_interrupted_replacement_is_rolled_back_on_the_next_open` (crash before the in-process rollback; reopen restores the snapshot); the existing crash-recovery test now simulates the crash before the rollback. On the 23:52 code the first two fail exactly as the reviewer described (annotations carrying 31.0 instead of 25.0; only P2 left).

**M28 — combined projections.** Removing a dataset now also deletes every `<checksum>.subset-*.review.vcf.gz` projection of its managed file (a combined projection is named by its selection, and any of them may carry the removed sample; rebuilt on demand). Ordinary (orphan-only) cleanup additionally reads each projection's `#CHROM` header and treats one that lists a sample no dataset of that file has any more as orphaned, so a combined projection left by an earlier build is reclaimed too; an unreadable header is left alone (the *projections* category still takes it). Test: `test_removing_a_dataset_deletes_combined_projections_that_carried_it` (three-sample file; fails on the old code).

**M30 — cohort `picked` backfill.** The backfill was keyed on the column's absence in the same startup, so an interruption between ALTER and backfill left every eligible row at 0 for good. It is now `_migrate_picked_backfill`: stamped `cohort_meta.picked_backfill = pick-fallback-v1` in the same transaction as the UPDATE; a stamp-less index with no pick at all (what an interruption leaves) is backfilled on the next open, and a stamp-less index that already carries picks — migrated by an earlier build, or indexed with PICK — is only stamped, so deliberate zeros are never changed and the table-wide correlated update runs at most once per database. Test: `test_interrupted_pick_migration_is_completed_on_the_next_open` (both cases).

**M32 — byte budget.** The export is written in binary mode (`open("wb")`, UTF-8 encoded per line), so `total_bytes` counts bytes, and `vcf_bytes` (file size) and the budget agree. Test: `test_sample_review_export_budget_counts_utf8_bytes` (a multi-byte sample name; a budget one byte under the true size is refused although the character count fits; fails on the old code).

**macOS path assertions.** `ChunkedMergeTests` compared the store's resolved path with an unresolved `/var/...` temp path; the fixture root is now resolved. The whole `test_cohort_store` suite (68 tests) passes on your Mac under Python 3.10, as does `test_sample_library`.
